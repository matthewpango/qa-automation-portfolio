# Первая публикация ParcelQuote на GitHub

Исходники и workflow подготовлены локально. Remote пока не настроен,
push не выполнялся. Шаблоны PR и ошибок начнут использоваться после публикации
в основной ветке. Значок успешного CI в README добавляется после реального запуска.

## Что входит в репозиторий

Код приложения, тесты, lockfile, Docker-конфигурация, ESLint, Playwright,
Allure-конфигурация и QA-документация. `.agents/qa-project-context.md` содержит
проектные правила и остаётся в Git. Установленные локальные скиллы, их lockfile,
зависимости, отчёты и traces исключены через `.gitignore`.

## Перед созданием репозитория

- Выберите имя репозитория и видимость. Подходящее описание:
  «Учебный сервис расчёта доставки: TypeScript, Playwright API/UI, Docker, Allure и GitHub Actions».
- Решите вопрос лицензии. Файл LICENSE пока не добавлен, лицензия не выбиралась.
- Проверьте авторство коммитов и email, которые попадут в опубликованную историю:
  `git log --format=fuller`. Эта инструкция не переписывает историю и не меняет авторство.
- Проверьте подготовленные файлы: `git status --short` и `git diff --cached --stat`.
  Для просмотра локальных исключений: `git status --short --ignored`.
- Создайте пустой репозиторий на GitHub, без автоматически созданных README,
  `.gitignore` и лицензии. Локальная история уже содержит README и конфигурацию.

## Подключение и первый push

Текущая локальная ветка: `feat/parcelquote`. Основной ветки `main` пока нет.
После получения URL пустого GitHub-репозитория выполняются следующие действия.
Замените `YOUR_ACCOUNT` и `YOUR_REPOSITORY` реальными значениями:

```sh
git branch -m main
git remote add origin https://github.com/YOUR_ACCOUNT/YOUR_REPOSITORY.git
git push -u origin main
```

Эти команды приведены для первой публикации; в ходе подготовки они не выполнялись.
Если remote уже появился или история GitHub-репозитория не пустая, сначала
сверьте состояние. Для устранения расхождений не требуется force push.
После публикации последующие изменения выполняются в отдельных ветках с PR в `main`.

Официальная инструкция: [добавление локального кода на GitHub](https://docs.github.com/en/migrations/importing-source-code/using-the-command-line-to-import-source-code/adding-locally-hosted-code-to-github).

## Проверка после публикации

1. Откройте Actions и дождитесь workflow `Tests` на основной ветке.
   Должны выполниться lint, TypeScript и все 207 проверок в Docker.
2. Скачайте `test-evidence` и проверьте логи, Playwright HTML и Allure.
   Для Allure поместите каталог `allure/` из архива в локальный checkout и
   используйте команду просмотра из README. Java не требуется.
3. В отдельной временной ветке создайте PR с намеренно неверным ожиданием теста.
   Подтвердите красный статус и доступные скриншот/trace/отчёт, затем закройте
   контрольный PR без слияния. Намеренную ошибку в `main` не переносите.
4. Проверьте восстановление истории Allure между двумя полными запусками
   одной Git-ссылки. Наличие cache в YAML само по себе не доказывает восстановление.
5. После появления реального статуса настройте правило ветки с обязательным
   check `tests`, затем проверьте блокировку слияния контрольного падающего PR.
6. Добавьте в README реальные ссылки на репозиторий и Actions, а также CI badge.
   Ссылки с вымышленным владельцем и значок неподтверждённого запуска не добавляются.

Публикация исходников и проверка CI не развёртывают приложение. Хостинг и CD
остаются отдельным решением.
