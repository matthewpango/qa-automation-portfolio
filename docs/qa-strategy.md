# Тестовая стратегия ParcelQuote

Версия: 1.0. Дата: 2026-11-09.
Owner: автор портфолио, QA Automation Engineer.
Статус: предлагаемая стратегия следующего этапа; новые тесты и CI ещё не реализованы.

### 1. Краткое описание

Цель: показать обоснованный тест-дизайн, автоматизацию на TypeScript и Playwright,
диагностику ошибок и воспроизводимый запуск через Docker и будущий CI.
Качество подтверждается покрытием рисков и независимыми ожидаемыми результатами.
Количество тестов и процент покрытия служат дополнительными сигналами.

Порядок работы: закрыть пробелы в расчёте и контракте, добавить HTTP API-набор
против контейнера, укрепить UI-проверки, затем подключить GitHub Actions и отчёты.
Календарный срок не согласован; этапы ниже завершаются по результату.

### 2. Объект, границы и источники

В области проверки:

- POST `/api/quote`, восемь обязательных полей и все документированные ответы.
- Расчёт веса, расстояния, обычной/экспресс-доставки и хрупкого груза.
- Десять городов, 90 междугородних направлений и запрет одинаковых городов.
- Форма: валидация, результат, ошибки сети, изменение параметров и фокус.
- Запуск образа, healthcheck и доступность страницы/API через опубликованный порт.
- Минимальные проверки доступности, безопасности входа и диагностики отказов.

За границами текущего этапа: БД, авторизация, платежи, сохранение расчётов,
реальные карты, точность километров по автодорогам, production-развёртывание,
нагрузочное тестирование и формальная сертификация WCAG. Этих функций или
согласованных требований в продукте нет. Расстояния учебные.

Источники: [README](../README.md), [междугородние маршруты](superpowers/specs/2026-11-09-intercity-routes.md),
`src/quote.ts`, `src/app.ts`, `src/routes.json`, `src/tariffs.json`,
`Dockerfile`, `compose.yaml`, `tests/`, `playwright.config.ts`.
При конфликте первоначального дизайна с новым решением о городах действует
последнее согласованное решение. Существующий код сам по себе не служит
доказательством правильности бизнес-правила.

### 3. Текущее состояние и форма набора

Снимок: `f31c7d4`, повторный запуск `npm test` 2026-11-09 завершился успешно.

| Уровень | Количество | Доля | Что действительно проверяется |
|---|---:|---:|---|
| Unit | 6 | 13,0% | Четыре проверки формулы, две проверки таблицы маршрутов |
| Интеграционный API | 34 | 73,9% | Fastify.inject, без реального TCP и Docker |
| Браузерный UI/E2E | 6 | 13,0% | Chromium и локальный Node-сервер на порту 3100 |
| Всего | 46 | ≈100% | Прошли в одном контрольном запуске |

Два браузерных сценария используют перехваты HTTP для ошибок и задержек;
остальные проверяют реальный расчёт или взаимодействие с формой. Все шесть
не следует выдавать за полные E2E против Docker. Проверка 500 использует
намеренно падающий маршрут только внутри тестового приложения.

HTTP API-набора Playwright против контейнера пока нет. Нет CI, сохранённого
baseline покрытия, накопленной статистики flaky-тестов, HTML-отчёта и Allure.
Сейчас репортёр Playwright `list`, trace сохраняется при отказе.
Браузерная часть контрольного запуска заняла 5,0 с на этой машине;
это не время будущего CI и не показатель производительности сервиса.

Набор имеет форму ромба с преобладанием API. Для сервиса с одним endpoint это
разумно: основная граница продукта находится в HTTP-контракте. Не переносить
проверки в браузер ради привычного инструмента или количества E2E.

Ориентир после этапа 3: около 20 unit, 48 API (inject + HTTP) и 8 браузерных
тестов, всего 76; доли 26,3% / 63,2% / 10,5%. Это бюджет размера набора,
не требование добавить лишние тесты. Окончательный объём определяется матрицей.

### 4. Риски и приоритеты

Оценки предложены автором стратегии по коду и изменениям проекта. Это экспертные
оценки, а не статистическая вероятность: production-истории и финансовых потерь
нет. Влияние и вероятность оценены по шкале 1–5; балл является их произведением.
Зоны: 1–4 низкая, 5–9 средняя, 10–14 высокая, 15–25 критическая.
P0 означает обязательную регрессию ядра, а не объявление production-инцидента.

| ID | Риск и последствие | Влияние | Вероятность | Балл | Приоритет и ответ |
|---|---|---:|---:|---:|---|
| R1 | Ошибка округления/доплат даёт неправильную цену | 4 | 3 | 12 | P0: независимые эталоны, unit и HTTP-композиции |
| R2 | Неверный город/маршрут или внутригородская доставка | 4 | 3 | 12 | P0: таблица, все направления, запреты в API и UI |
| R3 | API молча исправляет типы, принимает лишнее или меняет ответ | 4 | 3 | 12 | P0: контракт успеха/ошибок и негативная матрица |
| R4 | Поздний ответ или сетевой сбой оставляет неверную цену | 3 | 4 | 12 | P0: управляемая задержка, ошибка и повторный запрос |
| R5 | Форма недоступна с клавиатуры или на узком экране | 3 | 3 | 9 | P1: фокус, подписи, ошибки, адаптивность |
| R6 | Код проходит inject, но образ не запускается или порт недоступен | 3 | 3 | 9 | P0 smoke контейнера, P1 расширенная диагностика |

Разбор наиболее важных отказов:

| Отказ | Возможная причина | Как обнаружить | Предупреждение регрессии |
|---|---|---|---|
| Лишний оплачиваемый кг | Допуск точности или раннее округление | 1,00000000001 отклоняется; объёмный 1,0004 оплачивается как 2 | Отдельные эталоны на точность и переход через целый кг |
| Ошибка расстояния | Перестановка строк таблицы или доверие distanceKm клиента | 700 км для Москва → Санкт-Петербург, обратный маршрут, запрет distanceKm | Полнота таблицы + фиксированные бизнес-примеры |
| Неверная комбинация доплат | Хрупкость умножается вместе с основной суммой | Четыре строки таблицы решений ниже | Проверять составляющие и итог, не только общий totalRub |

### 5. Уровни, инструменты и распределение проверок

| Уровень | Назначение | Инструмент | Когда запускать |
|---|---|---|---|
| Статический | Типы и корректность импортов | Существующий TypeScript | Перед тестами |
| Unit | Ветви формулы, округление, свойства маршрутов | Существующий node:test | При изменении логики, каждый будущий PR |
| API внутри процесса | Схемы, валидация, обработчик 500, конфигурация | node:test + Fastify.inject | Каждый будущий PR |
| HTTP API | Публичный контракт и упаковка приложения | Playwright APIRequestContext, планируется | Против собранного Docker-образа |
| UI/E2E | Связь формы с API, состояния и работа пользователя | Существующий Playwright | Каждый будущий PR |
| Исследовательский | Неочевидные комбинации и удобство | Ручная сессия с заметками | При изменении формы и перед демонстрацией |

Не дублировать всю негативную API-матрицу через UI. Для общей валидации HTTP
проверять характерные классы; глубокие внутренние ветви оставлять в inject/unit.
Перехваты допустимы для сетевых отказов и гонок, но хотя бы один расчёт каждой
основной пользовательской ветви должен проходить через настоящее приложение.

Выбор инструментов уже ограничен стеком пользователя: TypeScript + Playwright.
Дополнительные раннеры не нужны. Оценки ниже предложены для этого репозитория,
по шкале 1–5; это не публичный сравнительный benchmark.

| Критерий | Вес | node:test + inject для внутреннего API | Playwright для HTTP и UI | Новый универсальный раннер |
|---|---:|---:|---:|---:|
| Соответствие имеющемуся коду | 35% | 5 | 5 | 3 |
| Соответствие стеку пользователя | 25% | 4 | 5 | 3 |
| Минимум поддержки и новых зависимостей | 25% | 5 | 5 | 2 |
| Подходящие проверки и диагностика | 15% | 4 | 5 | 4 |
| Взвешенный итог | 100% | 4,60 | 5,00 | 2,90 |

Инструменты первых двух столбцов дополняют друг друга. HTML-отчёт Playwright
и traces выбираются первыми; Allure добавляется позже, если демонстрирует
отдельную полезную задачу. Pact, БД, платные browser farms и шардирование сейчас
не соответствуют размеру или архитектуре продукта.

### 6. Тест-дизайн, данные и ожидаемые результаты

Подробная трассировка: [матрица покрытия](qa-coverage-matrix.md).

Техники: классы эквивалентности, граничные значения, таблица решений,
переходы состояний UI и проверки свойств. Для полей проверять валидные значения,
границы, пропуск, null и неверный тип. Проверка fragile обязана принимать false:
ложное значение не означает отсутствие обязательного поля.

Базовый пример: 2 кг, 10 × 10 × 10 см, Москва → Санкт-Петербург, 700 км.
Объёмный вес 0,2 кг; оплачиваемый 2 кг; 70 блоков расстояния.
До доплат: 100 + 100 + 700 = 900 ₽.

| Доставка | Хрупкий груз | Доплата экспресс | Доплата хрупкость | Итог |
|---|---|---:|---:|---:|
| Обычная | Нет | 0 ₽ | 0 ₽ | 900 ₽ |
| Обычная | Да | 0 ₽ | 100 ₽ | 1000 ₽ |
| Экспресс | Нет | 450 ₽ | 0 ₽ | 1350 ₽ |
| Экспресс | Да | 450 ₽ | 100 ₽ | 1450 ₽ |

Дополнительные независимые эталоны: Москва → Казань 820 км даёт 1020 ₽ для
той же обычной посылки; 0,1 кг, 41 × 61 × 2 см дают объёмный вес 1,0004 кг
и оплачиваемые 2 кг. Внутренние интервалы расстояния 10/11 км проверяются unit:
в HTTP-контракте пользователь расстояние больше не задаёт.

Ожидаемые цены задавать литералами из согласованных правил. Не вычислять их
через calculateQuote, getRoute или импорт активного тарифа в самом тесте.
Свойства вроде симметрии маршрута дополняют, но не заменяют числовые эталоны.
Все 90 направлений проверять на доступность; фиксированные примеры защищают
от ситуации, когда таблица симметрична, но содержит неверные согласованные значения.

Данные небольшие и детерминированные. Аккаунты, сидирование и очистка БД не нужны.
Изменения тарифов/таблицы проверять в изолированной копии или отдельном контейнере;
не переписывать конфигурацию общего запущенного сервиса при параллельных тестах.
Случайные данные пока не нужны. Если появятся, сохранять seed при отказе.

### 7. Окружения и воспроизводимость

| Окружение | Состояние | Назначение |
|---|---|---|
| Локальный Node | Существует | Unit/inject и разработка |
| Сервер Playwright, 127.0.0.1:3100 | Существует | UI; поднимается и останавливается раннером |
| Docker Compose, 127.0.0.1:3000 | Существует | Проверка образа, HTTP и демонстрация |
| GitHub Actions runner | Планируется | Чистая установка, образ, тесты и артефакты |
| Staging / production | Отсутствуют | Не подменять ими локальные проверки |

Lockfile, Node.js 24 и активные JSON-конфигурации входят в воспроизводимый запуск.
Текущий базовый образ закреплён тегом Node 24, не digest; для строгой повторяемости
будущего CI фиксировать/записывать digest образа и версию браузера.
Тесты против Docker должны получать baseURL извне и иметь явное управление
окружением. Текущая конфигурация Playwright жёстко запускает Node на 3100:
это отдельная запланированная доработка, а не уже готовая возможность.

### 8. Критерии входа и выхода

| Уровень | Вход | Выход |
|---|---|---|
| Unit | Правило и ожидаемый результат описаны | Все сценарии P0 формулы/маршрутов зелёные, нет пропущенных P0 |
| API/inject | TypeScript и unit проходят | Успех и ошибки соответствуют контракту, обязательные поля и типы проверены |
| HTTP API | Образ собран, контейнер healthy, порт доступен | P0 HTTP-набор зелёный, настоящие ответы соответствуют контракту |
| UI/E2E | API зелёный, браузер установлен | Основные пути и P0 переходы состояния проходят без перезапусков |
| Версия для демонстрации | Все применимые уровни зелёные, нет открытых блокирующих дефектов | Smoke именно собранного образа зелёный, приложены результаты и SHA |

Ошибка порта, неработающий Docker или отсутствие браузера означают блокировку
окружения, а не успешную проверку и не автоматически дефект продукта.
Нельзя подменять неудачный реальный запуск исключительно мокированным ответом.

### 9. Правила допуска изменений и CI

Ниже предложенные правила. Сейчас они не обеспечиваются CI: workflow ещё нет.

| Стадия | Предлагаемый порог | Реализация |
|---|---|---|
| PR | TypeScript зелёный; 100% обязательных unit/API/UI проходят; 0 skip/only в P0 | На этапе CI |
| Merge | Все обязательные PR-проверки зелёные для актуального SHA; 0 неразобранных P0-дефектов | После настройки GitHub и правил ветки |
| Обновление демонстрации | Healthy + HTTP smoke 200/400 + расчёт из UI того же образа проходят | Пока локальная проверка, позже отдельная CI-стадия |
| Nightly | После появления расписания: полный набор 100% зелёный; любое падение требует разбора | Не включать отдельное расписание, пока полный набор помещается в PR-бюджет |

Начать с одного Linux runner и Chromium. Сохранить логи контейнера, HTML-отчёт
и trace отказа независимо от успешности job; затем остановить тестовое окружение.
Не публиковать тела с секретами, переменные окружения и браузерные профили.
Текущий сервис секретов и аккаунтов не использует.

Повторный запуск применяется для диагностики, не превращает первый отказ
в незаметный успех. Автоматические retries сначала оставить равными нулю.
Кэш установки добавить после рабочего чистого запуска; шардирование отложить
до измеренной проблемы со временем, вместо его введения для десятков тестов.

### 10. Метрики и отчётность

Все пороги ниже предложены, а не представлены как согласованные SLA.

| Метрика | Текущее значение | Цель | Когда смотреть |
|---|---|---|---|
| P0-трассировка | См. статусы в матрице | 100% P0 строк имеют автоматизированные критерии | Перед завершением этапа API и каждым PR |
| Успех обязательного набора | 46/46 в одном запуске | 100%, без скрытых пропусков | Каждый запуск |
| Покрытие ветвей quote/routes | Не измерено | Измерить; ориентир ≥80%, все P0 ветви проверены независимо от процента | После расширения unit, затем PR |
| Время локального браузерного набора | 5,0 с, одна машина и один запуск | <2 мин на согласованной машине | При заметном росте набора |
| Время PR CI | CI отсутствует | Предлагаемый бюджет ≤10 мин после прогрева кэша | Первые 10 CI-запусков и при росте |
| Нестабильность | Нет накопленной выборки | 0 неразобранных нестабильных сценариев; целевой flaky rate <2% после ≥20 запусков | Еженедельно после появления CI |
| Диагностируемость отказа | List + trace при падении UI | 100% упавших CI-запусков сохраняют доступные отчёт и логи | Каждый отказ CI |

Flaky rate: число исполнений, где одинаковые код/данные/окружение дают
неодинаковый результат, делённое на все исполнения тестов за окно наблюдения.
Сетевой отказ окружения отдельно классифицируется. Один зелёный запуск
не доказывает нулевую нестабильность. Долю escaped defects, MTTR production
и throughput не считаем без соответствующего окружения и истории.

Первый отчёт: SHA, окружение, результат каждого уровня, найденные дефекты,
непроверенные области и ссылки на артефакты. Для портфолио полезен пример
пойманного дефекта с воспроизведением и регрессионным тестом, а не только зелёный скриншот.

### 11. Этапы внедрения и ближайшее действие

| Этап | Работа | Критерий окончания |
|---|---|---|
| 1. Тест-дизайн | Принять стратегию и уточнить P0 матрицу; усилить точность и таблицу доплат | Каждый P0 связан с проверяемым ожиданием; новые проверки ловят намеренно сломанную ветвь |
| 2. HTTP API | Playwright request против Docker; параметры окружения; успех, негатив, контракт, 413/415 | Все P0 API выполняются через настоящий HTTP, inject остаётся для внутренних ветвей |
| 3. UI | Закрыть пробелы матрицы, отдельно проверить клавиатуру и ошибочные ответы | Пользовательские P0 проходят, нет размножения арифметики через UI |
| 4. CI и отчёт | GitHub Actions, Docker lifecycle, HTML, traces, логи | Зелёный и специально падающий запуски дают правильный exit code и артефакты |
| 5. Измеренное расширение | Coverage, затем Firefox/WebKit, a11y, при необходимости нагрузка/Allure | Каждое расширение закрывает названный риск и имеет бюджет времени |

Этапы оцениваются после выполнения предыдущего, без выдуманных дат релиза.
Ближайшая реализация: создать HTTP API-набор на Playwright с baseURL контейнера,
перенести в него независимые примеры и негативные классы из матрицы. Текущие
inject-тесты не удалять до подтверждения равноценности покрытия.

### 12. Ответственность и сопровождение

Owner: QA Automation Engineer, автор портфолио. Он принимает бизнес-ожидания,
приоритеты и найденные дефекты; агент может готовить проверки и артефакты.
Организационная команда, бюджет и дедлайн не заданы; дополнительные роли не вводятся.

Пересматривать стратегию при изменении тарифа, API, списка городов, формулы,
состояний формы, версии браузера или среды исполнения, а также после дефекта,
пропущенного автоматизацией. В спокойный период пересмотр раз в квартал.
Изменённое требование обновляет матрицу и тесты одним изменением.
