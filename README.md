# ParcelQuote

Небольшой сервис расчёта стоимости междугородней доставки: JSON API и веб-форма на русском.
Учебный продукт для портфолио QA Automation Engineer на TypeScript и Playwright.
Тарифы вымышленные, сервис не оформляет отправления реальных перевозчиков.

## Запуск в Docker

Нужен Docker с поддержкой Linux-контейнеров и Docker Compose.
Из корня проекта:

```sh
docker compose up --build -d --wait
```

Страница: http://127.0.0.1:3000. Node.js и npm на компьютере не требуются.
Контейнер включает только runtime-зависимости и запускается от пользователя `node`.
Порт доступен только на локальном компьютере. Проверка здоровья обращается к странице сервиса.

```sh
docker compose logs -f
docker compose down
```

После изменения кода, `src/tariffs.json` или `src/routes.json` повторите команду запуска с `--build`:
файлы входят в образ, тома для хранения данных не нужны.
Если порт 3000 занят, поменяйте первую часть привязки в `compose.yaml`,
например на `127.0.0.1:3001:3000`, и откройте http://127.0.0.1:3001.

## Запуск без Docker

Нужны Node.js 24 или новее и npm.

```sh
npm ci
npm start
```

Страница: http://127.0.0.1:3000. `npm run dev` запускает сервер с перезапуском
при изменении исходников. Отдельной сборки нет: Node.js 24 выполняет TypeScript
с удалением типов. Проверка типов запускается отдельной командой.

Переменные окружения: `HOST` (по умолчанию `127.0.0.1`) и `PORT` (по умолчанию `3000`).
Пример для PowerShell:

```powershell
$env:PORT = '3001'
npm start
```

База данных, ключи доступа и внешние API не нужны. Расчёты не сохраняются.
Тарифы находятся в `src/tariffs.json`, города и учебные расстояния в `src/routes.json`.
После изменения перезапустите приложение.

## Параметры

| Поле API | Описание | Ограничения |
|---|---|---|
| weightKg | Фактический вес, кг | 0,1–30, шаг 0,01 |
| lengthCm | Длина, см | Целое число 1–100 |
| widthCm | Ширина, см | Целое число 1–100 |
| heightCm | Высота, см | Целое число 1–100 |
| originCity | Город отправления | Код города из списка ниже |
| destinationCity | Город назначения | Код другого города из списка ниже |
| deliveryType | Доставка | `standard` или `express` |
| fragile | Хрупкий груз | `true` или `false` |

Все границы включены. Все поля обязательны. Неизвестные поля, `null` и строки
вместо чисел отклоняются. В форме вес можно вводить через точку или запятую,
в JSON используются числа с точкой. Значения `1.250` и `1.25` эквивалентны.

## Города и маршруты

| Город | Код |
|---|---|
| Москва | `moscow` |
| Санкт-Петербург | `saint-petersburg` |
| Казань | `kazan` |
| Нижний Новгород | `nizhny-novgorod` |
| Воронеж | `voronezh` |
| Ростов-на-Дону | `rostov-on-don` |
| Волгоград | `volgograd` |
| Самара | `samara` |
| Краснодар | `krasnodar` |
| Екатеринбург | `yekaterinburg` |

В форме нужно выбрать город отправления и город назначения. Одинаковые города
запрещены: доступны только междугородние перевозки. Расстояние определяет сервер,
его нельзя передать или подменить в запросе.

Таблица в `src/routes.json` содержит **условные учебные расстояния**, а не точные
километры по автодорогам. Порядок строк и столбцов соответствует массиву `cities`.
Обратный маршрут имеет такое же расстояние. Доступны все 90 направлений между
разными городами. Например, Москва → Санкт-Петербург: 700 км, Москва → Казань: 820 км.

Запросы старой версии с полем `distanceKm` больше не принимаются: вместо него
обязательны `originCity` и `destinationCity`. В ответе `distanceKm` сохраняется
как вычисленное сервером расстояние.

## Расчёт

1. Объёмный вес: длина × ширина × высота / 5000.
2. Расчётный вес: больший из фактического и объёмного.
3. Каждый начатый килограмм расчётного веса стоит 50 ₽.
4. Каждый начатый блок 10 км стоит 10 ₽.
5. Базовый сбор: 100 ₽.
6. Экспресс умножает сумму пунктов 3–5 на 1,5.
7. Хрупкий груз добавляет 100 ₽ после применения множителя.

Вес до выбора оплачиваемых килограммов не округляется.
Ограничение 30 кг относится к фактическому весу, объёмный может быть больше.
При текущих тарифах денежные результаты целые. При переходе к дробным тарифам
нужно отдельно определить денежную точность.

## API

`POST /api/quote`, `Content-Type: application/json`.

Пример запроса, обычная посылка 2 кг из Москвы в Санкт-Петербург:

```json
{
  "weightKg": 2,
  "lengthCm": 10,
  "widthCm": 10,
  "heightCm": 10,
  "originCity": "moscow",
  "destinationCity": "saint-petersburg",
  "deliveryType": "standard",
  "fragile": false
}
```

Вызов из PowerShell:

```powershell
$parcel = @{
  weightKg = 2; lengthCm = 10; widthCm = 10; heightCm = 10
  originCity = 'moscow'; destinationCity = 'saint-petersburg'
  deliveryType = 'standard'; fragile = $false
}
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:3000/api/quote' `
  -ContentType 'application/json' -Body ($parcel | ConvertTo-Json)
```

Успешный ответ, HTTP 200:

```json
{
  "actualWeightKg": 2,
  "volumetricWeightKg": 0.2,
  "chargeableWeightKg": 2,
  "billedWeightKg": 2,
  "distanceBlocks": 70,
  "baseCostRub": 100,
  "weightCostRub": 100,
  "distanceCostRub": 700,
  "subtotalRub": 900,
  "deliveryMultiplier": 1,
  "expressSurchargeRub": 0,
  "fragileSurchargeRub": 0,
  "totalRub": 900,
  "currency": "RUB",
  "originCity": "moscow",
  "destinationCity": "saint-petersburg",
  "originCityName": "Москва",
  "destinationCityName": "Санкт-Петербург",
  "distanceKm": 700
}
```

Для того же запроса `deliveryType: "express"` даёт 1350 ₽.
Дополнительно `fragile: true` даёт 1450 ₽.

Ошибки:

- `400`: неверные или пропущенные поля, неизвестные поля, некорректный JSON.
- `413`: слишком большое тело запроса.
- `415`: Content-Type отличается от application/json.
- `500`: внутренняя ошибка без стека и технических подробностей.

```json
{"errors":[{"field":"weightKg","message":"Вес должен быть от 0,1 до 30 кг с точностью до 0,01 кг."}]}
```

Для ошибки всего тела `field` равен `null`. Ответ может содержать несколько
ошибок; порядок не фиксирован. Изменённый после отправки запрос не обновляет
результат формы устаревшей ценой.

## Автотесты

Подход к дальнейшей автоматизации описан в [тестовой стратегии](docs/qa-strategy.md).
Требования, риски, существующие проверки и пробелы сведены в
[матрицу покрытия](docs/qa-coverage-matrix.md).

```sh
docker compose --profile test run --build --rm tests
```

Это основной способ запуска локально и в CI. Сервис `tests` содержит Node.js 24,
Playwright 1.65.0 и Chromium; Node.js и браузер на хосте не нужны.
Compose ожидает healthy у `app`, затем запускает в тестовом контейнере
TypeScript, unit, внутренние интеграционные, API- и UI-тесты.
Контейнеры общаются по `http://web:3000` во внутренней сети.
После завершения контейнер тестов удаляется, приложение продолжает работать.
Ненулевой exit code тестов передаётся вызывающей команде.

Только API или только UI, тоже в контейнере:

```sh
docker compose --profile test run --build --rm tests npm run test:api
docker compose --profile test run --build --rm tests npm run test:ui
```

Исходники и зависимости входят в образ `Dockerfile.tests`; после их изменения
используйте `--build`. Версия базового Playwright-образа должна совпадать
с версией `@playwright/test` в lockfile. Отчёты монтируются на хост в
`playwright-report/`, `test-results/` и `allure/`, поэтому переживают удаление контейнера.

Команды npm выполняются внутри тестового контейнера:

- `npm run typecheck`: строгая проверка TypeScript.
- `npm run test:unit`: формула и таблица маршрутов через node:test.
- `npm run test:integration`: две внутренние проверки через Fastify.inject:
  обработка 500 и изолированная смена конфигурации тарифов.
- `npm run check`: TypeScript, unit и внутренние интеграционные проверки.
- `npm run test:api`: 63 API-теста на Playwright, только HTTP без запуска браузера.
- `npm run test:ui`: 11 браузерных сценариев Playwright в Chromium.
- `npm test`: все перечисленные проверки.

В одной конфигурации Playwright два проекта: `api` и `chromium`.
В Compose `BASE_URL` уже задан для контейнерной сети, поэтому раннер использует
готовое приложение и не запускает дополнительный сервер. Вручную выставлять
переменные на хосте не нужно. Все команды автотестов выполняйте через сервис `tests`.

API-набор находится в `tests/api/`: четыре сочетания доплат, точность и границы
веса/габаритов, 90 направлений, запрет всех 10 внутригородских маршрутов,
обязательные поля и неверные типы, контракты JSON-ответов, HTTP 400/413/415.
Числовые ожидания заданы независимо от кода расчёта. Контракты проверяют точный
набор ключей и тип каждого поля, без добавления новых зависимостей.
Лимит JSON-тела сервиса составляет 1 МБ; заведомо большой Content-Length
отклоняется до парсинга, чтобы клиент получил 413 вместо сброса соединения.
Нет публичного способа специально вызвать 500: эту ветвь проверяет внутренний тест.

Smoke-набор проверяет реальный расчёт, ошибки, дробный вес, выбор городов,
запрет внутригородского маршрута, повторный запрос, устаревший ответ и узкий экран.
Серверные проверки также проверяют полноту и симметрию таблицы маршрутов.
Для сбоев сети используются перехваты Playwright.
Трейс сохраняется при неудаче в `test-results/`.

API-набор работает через настоящий HTTP между контейнерами.
Кроссбраузерность и нагрузочные тесты остаются отдельными этапами.
Используются list-, HTML- и Allure-репортёры. Скриншоты и trace
сохраняются при неудаче и доступны во вложениях Allure.

## Отчёт и GitHub Actions

Allure 3 автоматически формируется после `test:api`, `test:ui` и `test:playwright`,
включая запуск через `npm test`. Полный отчёт включает 74 Playwright-теста;
6 unit и 2 внутренних интеграционных проверки остаются в логах.
Отчёт создаётся и при падении теста, исходный exit code сохраняется.
Генератор работает на Node.js внутри контейнера, Java не требуется.

```sh
docker compose --profile test run --rm --no-deps -p 127.0.0.1:8080:8080 tests npm run allure:open
```

Откройте http://127.0.0.1:8080. После просмотра остановите сервер через Ctrl+C.
`allure/results/` содержит исходные результаты, `allure/report/` готовый отчёт,
`allure/history.jsonl` историю запусков. Файлы сохраняются на хосте.
Каждый запуск показывает только свои результаты, сохраняя историю предыдущих.
В CI история восстанавливается из cache для той же Git-ссылки и сохраняется
после полного прогона. Тренды требуют накопления реальных запусков.
Версия `glob` закреплена через npm overrides для устранения уязвимости
транзитивной зависимости генератора.


После запуска Playwright HTML-отчёт находится в `playwright-report/`:

```sh
docker compose --profile test run --rm --no-deps -p 127.0.0.1:9323:9323 tests npx playwright show-report --host 0.0.0.0
```

Отчёт доступен по http://127.0.0.1:9323. После просмотра остановите сервер
через Ctrl+C.

Workflow: `.github/workflows/tests.yml`, job `tests`.

| Событие | Проверки |
|---|---|
| Push в рабочую ветку | Workflow lint, TypeScript, unit, внутренние интеграционные |
| Pull request | Всё выше + сборка Docker + все API и UI |
| Push в основную ветку | Полный набор, включая Docker |
| Ручной workflow_dispatch | Полный набор, включая Docker |

И приложение, и автотесты в CI запускаются через Compose.
В runner не устанавливаются Node.js, npm-зависимости и Chromium для запуска тестов:
они находятся в тестовом образе. Быстрые проверки идут в `tests` без приложения,
полный набор ожидает healthy у `app` и проверяет его по контейнерному адресу.
При ошибке сохраняются доступные `artifacts/`, `playwright-report/`, `test-results/` и `allure/`:
логи проверок и контейнера, HTML-отчёт, traces и скриншоты отказов.
Срок хранения артефактов: 14 дней. Окружение останавливается в завершающем шаге,
включая ошибочные запуски. Повторные попытки тестов не включены.

Workflow подготовлен и проверен локально. Для реального запуска нужен GitHub-репозиторий
с этими файлами: remote пока не настроен. Публикация и включение обязательного
статуса `tests` в правилах ветки остаются действиями на GitHub; локальный workflow
сам по себе не устанавливает branch protection и не развёртывает production.

Контрольный набор: 6 unit, 2 внутренних интеграционных, 63 API и 11 UI,
всего 82. Он прошёл на Windows и в Linux с Node.js 24 и Playwright 1.65.0.
Отказной прогон отдельно подтвердил ненулевой exit code и наличие отчёта,
trace и скриншота. Загрузка артефактов именно в GitHub пока не проверена.

## Структура

```text
src/                 расчёт, тарифы, API и запуск
public/              форма, стили и браузерный JavaScript
tests/               проверки расчёта, API и UI
docs/superpowers/    согласованное описание и план
docs/agents/         правила работы инженерных навыков
```

Проект предназначен для локального запуска. Публикация в GitHub и размещение
сервиса в интернете в текущую версию не входят.
